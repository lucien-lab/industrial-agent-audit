# 技术决策记录

记录日期：2026-10-22。以下为规划决策，不代表相应组件已部署。

## 决策 001：采用 PostgreSQL 与 pgvector

状态：接受，具体版本待验证。

关系数据、时间窗口查询、文档元数据与审计关联都需要一致的持久化基础。在同一数据库内管理向量可降低初期部署及关联查询的复杂度。代价是时序写入与向量查询共享资源，需要在后续实测索引、容量和隔离效果。达到容量或延迟瓶颈时再评估专用向量库、时序扩展或独立存储。

## 决策 002：优先使用 MetroPT-3

状态：接受，字段及适用性仍待核验。

选择理由是其工业设备运行背景、多变量时序和公开来源便于构建可追溯的数据查询与运维演示。来源依据见 [数据来源说明](data_sources.md)。限制包括缺乏逐样本标签、来源描述存在待核验处，以及尚未获得确定匹配的技术说明书。不将数据集选择等同于已经具备完整诊断依据。

## 决策 003：RAG、Agent 与 Audit 解耦

状态：接受。

RAG 提供知识证据，Agent 组织业务执行，Audit 独立检查可观察过程与结果。独立契约允许分别替换检索模型、编排策略或评审器，也便于单独评估。避免让 Agent 自述“正确”直接成为审计结论。共享事件与引用标识，不共享隐藏推理或将审计实现嵌入工具逻辑。

## 决策 004：初期采用模块化单体

状态：接受。

当前目标是验证完整 AI 应用开发链路，规模和负载尚不明确。模块化单体可降低服务发现、跨服务事务、消息队列与部署维护成本。通过清晰的目录与输入输出契约保留拆分空间；只有出现独立扩缩容、任务隔离或团队协作需求时才重新评估微服务。

## 决策 005：只读运维助手与独立事后审计

状态：接受。

初期仅查询数据和知识并提供辅助建议，不控制设备。权限、参数限制和预算在执行时落实，事后审计评估证据与行为。Agent-Probe 是本项目内部模块名；具体外部产品或库尚未决定。原始回答与审计结果分别保存，失败和无法判定有独立状态。

## 决策 007：源时间按“未知时区”存储

状态：接受，已实现（阶段 1B）。

源时间戳无偏移、官方未声明时区。采用 `timestamp without time zone` 保存，同时保留
`source_timestamp_raw` 原文并用 CHECK 约束保证二者一致，来源表记录
`timezone_status='unknown'`。备选方案（按 Europe/Lisbon 解释、统一转 UTC）都会引入
最多 1 小时的静默偏移，且无法从数据本身证明，因此不采用。代价是跨时区比较需要业务层
明确约定，本阶段不做任何跨时区换算。

## 决策 008：模拟量使用 `numeric(8,4)`，并以导入期校验代替四舍五入

状态：接受，已实现（阶段 1B）。

实测原始文本是 4 位小数值的 float64 序列化噪声（`|raw−round(raw,4)|` 最大 2.84e-14，
全量 1,516,948 行无一超过 1e-9），因此 `numeric(8,4)` 可无损还原真实测量值，并保留
“逐位相同”的冻结判定语义。若出现真实精度超过 4 位小数的输入，导入直接中止而不是静默
四舍五入。未采用 `float8`（破坏逐位比较与量化精度）。

## 决策 009：事实表主键使用 BIGINT，维度表保留 UUID

状态：接受，已实现（阶段 1B）。

`sensor_readings`/`data_gaps`/`ingest_runs` 使用 `bigint identity`；`equipment`/`data_sources`/
`fault_events` 保留 UUID。理由：千万级事实表以 COPY 批量写入为主，顺序键的索引局部性与体积
优于随机 UUID；业务身份由 `(source_id, source_row_number)` 唯一约束保证，不依赖主键。
这是对阶段 0“实体主键拟采用 UUID”的有意偏离，迁移与文档均已记录。

## 决策 010：质量标记分为行级与窗口级两类

状态：接受，已实现（阶段 1B）。

行级标记（`sensor_readings.quality_flags` 位掩码，`frozen-v1`）只描述单条记录；
采样缺口属于“两条记录之间”的缺陷，写入 `data_gaps` 表；覆盖率由函数
`sensor_coverage()` 按行口径与时间口径分别返回。冻结候选只标记、不删除、不插值。
理由：把窗口缺陷塞进单行标记会造成错误归因；删除或插值会伪造原始测量数据。

## 决策 011：测试与迁移只允许操作以 `_test` 结尾的库

状态：接受，已实现（阶段 1B）。

`backend/tests/conftest.py` 在会话开始时校验测试库名，`scripts/migrate.sh down-test`
同样校验；含真实数据的库禁止执行 `downgrade`。理由：回滚测试与 TRUNCATE 会破坏证据链，
而“回滚是否可用”完全可以在隔离库中验证。
