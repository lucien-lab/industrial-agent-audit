# RAG 评估（阶段 2）

- 评估日期：2026-10-22
- 评估对象：`bge-m3`（1024 维）+ `qwen2.5:7b-instruct`，知识库 6 份文档 / 131 页
- 原始结果：`knowledge/eval/rag_eval_summary.json`（完整版含证据与 Prompt 统计，位于
  `data/processed/knowledge/rag_eval.json`，该目录按项目约定不入 Git）
- 复现命令：

```bash
python scripts/evaluate_rag.py --out data/processed/knowledge/rag_eval.json
```

## 1. 评估集

52 条问题（`knowledge/eval/questions.json`），每条都有人工核对的**预期证据页码**，
不是由模型生成的真值。

| 类别 | 数量 | 说明 |
| --- | ---: | --- |
| `sensor_field` | 12 | TP2/TP3/H1/DV_pressure/Motor Current/COMP/TOWERS/MPG/LPS/Oil Level/Caudal Impulse 等字段含义 |
| `paper` | 8 | APU 结构、采集链路、FMEA、三次故障、评估协议 |
| `principle` | 12 | 容积式/动力式、往复/螺杆/离心、储气、P/C、干燥、泄漏、维护、稳压 |
| `identifier` | 5 | CAGI、acfm/bhp、psig、DOE/EE-1340、FMEA |
| `multi_doc` | 4 | 需要同时引用数据集文档与通用资料 |
| `unknown` | 5 | 厂商型号、额定参数、换油周期、指定日期故障、报警代码 |
| `model_mismatch` | 3 | Atlas Copco GA30、GA37、Kaeser ASD 40 |
| `irrelevant` | 3 | 天气、Python/CSV、写诗 |

其中 **41 条可回答**（参与检索指标），**11 条必须拒答**（`unknown` + `model_mismatch` + `irrelevant`）。

### 1.1 相关性口径

`expected` 中每条是一项**证据需求**：

- 检索到的 Chunk 与需求满足 `doc_key` 相同、且 `[page_start, page_end]` 与 `pages` 中任一页有交集 → 该需求满足；
- `also_ok` 允许同一需求由另一份文档/页码满足（例如检漏方法既可引 Tip Sheet #3 也可引 Sourcebook）；
- 多文档题按需求分别计分（2 条需求各占 0.5）。

这是**页面级**代理指标，不是 Chunk 级语义判定。它的优点是不依赖具体切分版本，可在
`fixed-v1` 与 `structural-v1` 之间公平比较；缺点是“页码命中”不等于“检索到的这一段就能回答”
（见 §5.2 的 Q15/Q41 案例）。

## 2. 检索指标定义

| 指标 | 定义 |
| --- | --- |
| Recall@5 | 每题的“已满足需求数 / 需求总数”，41 条可回答题取宏平均 |
| Hit Rate@5 | Top-5 至少满足一项需求的题目占比 |
| MRR@10 | Top-10 中第一条相关结果的倒数排名，宏平均 |
| Precision@5 | Top-5 中相关结果数 / min(5, 返回数) |

**阈值**：本阶段没有预注册目标阈值。开发过程中先建立了指标定义与题目，再跑最终结果；
报告中只陈述观测值，不做事后挑选。此点列为方法学不足（§7）。

## 3. 检索结果

### 3.1 三种方法 × 两种切分（41 题）

| 切分 | 方法 | Recall@5 | Hit@5 | MRR@10 | Precision@5 | 平均耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| structural-v1 | vector | 0.878 | 0.927 | 0.685 | 0.371 | 119 ms |
| structural-v1 | keyword | 0.561 | 0.585 | 0.486 | 0.258 | 11 ms |
| **structural-v1** | **hybrid** | **0.939** | **0.976** | **0.784** | **0.390** | 128 ms |
| fixed-v1 | vector | 0.829 | 0.854 | 0.647 | 0.278 | 115 ms |
| fixed-v1 | keyword | 0.561 | 0.585 | 0.468 | 0.245 | 13 ms |
| fixed-v1 | hybrid | 0.878 | 0.902 | 0.769 | 0.337 | 131 ms |

主要结论（基于上表，不外推）：

1. **混合检索优于任一单路**：structural 下 Recall@5 从 0.878（向量）/0.561（关键词）提升到 0.939，
   MRR@10 从 0.685 提升到 0.784；固定切分下同样成立（0.829 → 0.878）。
2. **结构感知切分在本知识库上更好**：同样方法下 Recall@5 提升 0.05–0.06，MRR@10 提升 0.01–0.04。
   这不是“结构感知必然更优”的证明——本库英文技术文档多、标题层级明显，结论只对当前语料成立。
3. 关键词检索单独使用时对中文语义问题几乎无效（见 §3.2），但对精确标识符非常有效。

### 3.2 分类别（structural-v1）

| 类别 | vector Recall@5 / MRR@10 | keyword | hybrid |
| --- | --- | --- | --- |
| sensor_field (12) | 0.917 / 0.711 | 0.917 / 0.833 | **1.000 / 0.875** |
| paper (8) | 1.000 / 0.844 | 0.500 / 0.417 | 1.000 / 0.844 |
| principle (12) | 0.917 / 0.607 | **0.167** / 0.069 | 0.917 / 0.656 |
| identifier (5) | 0.800 / 0.695 | **1.000 / 0.750** | **1.000 / 1.000** |
| multi_doc (4) | 0.500 / 0.508 | 0.250 / 0.500 | 0.625 / 0.508 |

解读：

- **标识符类**：关键词召回 100%，向量只有 80%；混合后 MRR 达到 1.0。
  这直接支持“纯向量无法稳定处理 TP2、DV_pressure、DOE/EE-1340 等精确标识符”的判断。
- **原理类**：中文问题 + 英文文档，关键词 bigram 几乎不命中（Recall 0.167），必须依赖
  多语言 Embedding；混合检索在这里等价于向量检索，没有额外收益也没有损失。
- **多文档类**：最高只有 0.625。单条查询很难同时把两份不同文档排进 Top-5，
  这是本阶段明确的失败类型，需要查询分解或多轮检索（未实现）。

### 4.2 人工复核

人工逐条阅读回答、引用标签与引用原文（`knowledge/eval/generation_manual_review.json`），
按 `knowledge/eval/questions.json` 中的 rubric 标注：

| 维度 | yes | partial | no |
| --- | ---: | ---: | ---: |
| 回答有证据支持（`evidence_supported`） | 42 | 7 | 3 |
| 引用正确（`citation_correct`） | 36 | 10 | 6 |
| 出现无证据断言（`unsupported_claims`，yes 表示**有**问题） | 2 | 4 | 46 |

- 有证据支持：42/52 = **80.8%** 完全成立，7 条部分成立，3 条不成立。
- 引用正确：36/52 = **69.2%** 完全正确；10 条部分正确（页码对但引文不是支撑句、
  或只引了多文档中的一侧），6 条错误（引用了无关页或答案被拒）。
- 编造内容：2 条明显（Q23 的“部分负载效率更高”、Q15 的“文档未指出 FMEA”），4 条部分
  （Q28 的 –40°F、Q38 的系统压力对应、Q39 的检漏方法、Q40 的 LPS 引用）。

复核由单人完成，没有第二评审人，也没有一致性系数；这是本阶段评估的主要方法学限制。

## 5. 开发过程中被评估暴露并修复的问题

1. **关键词 SQL 运算符优先级错误**：`A OR B OR C AND filter` 使过滤条件只作用于 tsvector 命中的行，
   导致 `fixed-v1` 与 `structural-v1` 的 Chunk 混入同一结果。修复为 `(A OR B OR C) AND filter` 后，
   两种切分的指标才出现应有差异。
2. **“证据不足”状态被引用覆盖**：模型明确说“不足以确认……但……”，只要带引用就被标成 `answered`。
   改为“模型判定不足即 `insufficient_evidence`”。
3. **引用标签错位**：模型常把同一页另一段落的标签写错。加入 `support_quotes` 逐字校验与
   唯一匹配时的标签重映射后，引用原文可机器验证。
4. **越界误判**：最初把“报警代码 E-204”当成编程问题拒答；调整规则后，报警/故障代码仍属知识库范围。
5. **未知型号防不住**：`ASD 40`（字母 + 空格 + 数字）最初没有识别，模型拿通用资料的压力值回答；
   扩展型号检测后改为确定性拒答。

## 6. 结论

- 在本知识库与评估集上，**混合检索（RRF）优于纯向量与纯关键词**，结构感知切分优于固定切分；
- 有证据支持的回答占 80.8%（人工），必拒答题 100% 拒答、0 条编造参数；
- 主要剩余问题不是“检索不到”，而是**多文档联合检索**与**引用粒度**（页码对但段落不对）；
- 生成侧的主要风险是 7B 模型的错误拒答与保守句式，而不是编造参数——这与“宁可不答”的
  产品取向一致，但会牺牲可用性。

## 7. 方法学限制

- 单一评审人，无标注一致性检验；
- 页面级相关性是代理指标，不能证明 Chunk 内部足以回答；
- 52 题规模偏小，未做置信区间；
- 没有预注册阈值，属于探索性评估；
- 只评估中文提问 + 英文文档，未覆盖中文文档与英文提问；
- LLM 输出存在随机性（temperature=0 仍非完全确定），换一次运行指标会小幅波动；
- 未评估成本（本方案为本地模型，只有电费/时间成本，没有 API 计费数据）。
